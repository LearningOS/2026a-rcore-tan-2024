# 第八章实验报告：并发

## 一、实现功能总结

实现进程级死锁检测开关，分别维护互斥锁和信号量的可用资源、分配记录与待满足请求。获取资源前检查是否存在可完成的线程序列，不安全时返回 `-0xDEAD` 并撤销请求；在释放、唤醒和线程退出时同步更新记录。适配条件变量的释放与重新加锁，恢复支持跨页写入的 `sys_get_time`，通过本章及前序基础测试。

## 二、问答作业

### 1. 在我们的多线程实现中，当主线程（即 0 号线程）退出时，视为整个进程退出，此时需要结束该进程管理的所有线程并回收其资源。

#### 1.1 需要回收的资源有哪些？

首先需要阻止进程中的其他线程再次运行，再按引用关系回收资源，主要包括：

- 线程的用户资源：用户栈、TrapContext 所占的物理页面和对应映射，以及线程 ID。
- 线程的内核资源：内核栈及其映射、内核栈编号、TaskControlBlock 等对象占用的内存。
- 进程共享资源：代码、数据、堆和其他用户页面，页表及地址空间管理结构，文件描述符表持有的文件、管道等引用。
- 同步与调度资源：互斥锁、信号量、条件变量及其等待队列，就绪队列和定时器中的线程引用，以及本次增加的资源分配和请求记录。
- 进程管理资源：全局 PID 到 PCB 映射中的引用，以及最后回收 PCB 时归还的 PID。子进程需要交给初始进程管理，退出码等等待信息则需保留到父进程回收。

当前代码先取出各线程的 `TaskUserRes`，再释放用户资源，随后调用 `recycle_data_pages` 清理共享用户页面，避免同一页面重复回收。由于 `TaskUserRes` 的析构过程也会访问 PCB，应先收集这些资源、释放 PCB 的独占借用，再执行析构，避免重复借用。

内核栈不能在仍使用它时释放。当前框架通过 `stop_task` 暂时保留正在退出的主线程引用，待切换到其他内核栈后再安全释放。PCB 则会作为僵尸进程保留必要的退出信息，最终由父进程的 `waitpid` 回收。

#### 1.2 其他线程的 TaskControlBlock 可能在哪些位置被引用，分别是否需要回收，为什么？

| 引用位置 | 退出时的处理及原因 |
| --- | --- |
| `ProcessControlBlockInner.tasks` | 清除线程表中的引用；否则进程仍会持有这些线程对象，内核栈等资源无法最终回收。 |
| `TaskManager.ready_queue` | 移除属于退出进程的就绪线程，避免调度器再次运行已失去用户资源的线程。 |
| 定时器队列 `TIMERS` | 移除等待超时的线程引用，避免定时器到期后把已终止线程重新唤醒。 |
| 互斥锁、信号量和条件变量的等待队列 | 随同步对象清理而释放引用。这些对象属于当前进程，无需把其中的线程重新加入就绪队列。 |
| `Processor.current`、退出函数中的局部变量 | 正在退出的线程需要先从处理器取出；局部引用在安全位置释放。不能为了立即减小引用计数而提前释放仍在使用的内核栈。 |
| `TaskManager.stop_task` | 当前框架有意暂留正在停止的主线程，待其不再使用内核栈后再释放。 |

这些位置保存的通常是 `Arc<TaskControlBlock>`。清除线程表并不等于立即销毁 TCB，只有所有强引用都释放后，TCB 及其内核栈才能最终析构。若同步对象或其他内核局部变量仍持有引用，也需要考虑它们的生命周期。

本次死锁检测记录只保存线程编号和资源计数，不保存 TCB 的强引用。线程退出时清除对应的分配和请求记录，避免线程 ID 复用后继承旧记录；这不等于无条件归还所有同步资源，例如信号量的 `down` 可以表示一次已经完成的资源消耗。

### 2. 对比以下两种 Mutex 中的实现，二者有什么区别？这些区别可能会导致什么问题？

题目中的 `Mutex1` 在 `lock` 中循环检查状态，并在 `unlock` 时先清除 `locked`，再唤醒一个等待线程；`Mutex2` 的 `lock` 只检查一次，如果有等待者，`unlock` 保持 `locked` 为真并唤醒一个线程，直接将锁交给它。

| 对比项 | Mutex1 | Mutex2 |
| --- | --- | --- |
| 唤醒后的行为 | 返回循环重新竞争锁，只有检查到空闲才进入临界区。 | 从阻塞处恢复后直接返回，认为已经获得锁。 |
| 存在等待者时的解锁 | 将锁设为空闲后唤醒等待者。 | 保持锁定状态，将锁直接交给选中的等待者。 |
| 新到达线程能否抢先获得锁 | 可以在被唤醒线程恢复执行前取得锁。 | 不能抢走已经交给等待者的锁。 |
| 主要影响 | 可能发生反复唤醒、再次阻塞，并使某些等待者长期得不到锁。 | 减少重复竞争，但依赖准确的唤醒和锁交接关系。 |

对于 `Mutex1`，例如线程 A 解锁并唤醒 B 后，线程 C 先运行并取得锁，B 恢复后发现锁仍被占用，只能重新排队。循环检查保证了互斥，但如果 C 一类的新到达线程不断抢先，B 可能饥饿。因此，即使等待队列按先入先出组织，也不能据此保证实际获取锁的顺序。

对于 `Mutex2`，被唤醒线程不再检查 `locked`，因此唤醒必须表示锁已经交给它，不能有无关或重复唤醒。其等待队列、线程阻塞状态和所有权交接必须保持一致；在多核或可抢占内核中，还需要保证入队、阻塞与唤醒操作之间不会丢失通知。本次框架中的阻塞互斥锁采用这一交接方式，使用 `wakeup_task` 更新线程状态并加入就绪队列。

两种方案的 `lock` 和 `unlock` 不能随意混用。如果用 `Mutex1` 的解锁方式配合 `Mutex2` 的加锁方式，锁可能已经被其他线程抢走，而被唤醒者仍直接进入临界区，破坏互斥。如果用 `Mutex2` 的解锁方式配合 `Mutex1` 的加锁方式，被唤醒者又会看到 `locked` 为真而重新阻塞，可能导致没有线程实际持锁、锁却无法继续交接。
